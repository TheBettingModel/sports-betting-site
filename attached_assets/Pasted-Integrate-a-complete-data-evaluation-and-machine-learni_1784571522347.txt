Integrate a complete data, evaluation, and machine-learning feedback system into The Betting Model.

## Central requirement

The existing TBM FastAPI backend and Neon PostgreSQL database must remain the single source of truth.

Do not create a disconnected prediction model inside the frontend.

The application must collect data, save every prediction, grade every result, evaluate model performance, create reproducible training datasets, test proposed improvements, and deploy only approved model versions.

The system must improve through controlled historical learning and validation. It must not automatically modify the production model after each individual win or loss.

Never delete or overwrite an original prediction snapshot after a game begins.

## 6. Data leakage prevention

A prediction or training row may use only information available before its data cutoff timestamp.

Never use:

* Final scores
* Closing lines when predicting earlier prices
* Confirmed information released after the prediction
* Season statistics containing the game being predicted
* Future injury or lineup updates
* Any postgame feature

Add automated leakage tests to the dataset-building pipeline.

## 9. Probability calibration

Build calibration reports that compare predicted probabilities with actual outcomes.

Use probability buckets and calibration curves.

Provide model-calibration methods that can be trained on validation data without modifying historical predictions.

Do not treat the frontend confidence score as an arbitrary display value. Confidence should be derived from measurable model information and calibrated historical performance.

## 11. Sport-specific model pipelines

Use separate training and evaluation pipelines for different sports and markets.

Do not train one generic model to replace all TBM sport models.

Keep shared utilities for:

* Data validation
* Vig removal
* Calibration
* Market intelligence
* Line shopping
* Performance evaluation
* Model registration
* Backtesting

Allow sport-specific models to feed the existing Universal POD and ranking systems.

## 12. Backtesting

Create a walk-forward backtesting system.

For every proposed model:

* Train only on prior data
* Validate on later data
* Test on unseen chronological data
* Use realistic odds available at the intended prediction time
* Compare with the current production model
* Compare with implied market probability
* Calculate financial and probabilistic metrics
* Record sample sizes
* Test multiple seasons where available
* Include transaction assumptions and realistic line availability

Do not approve models based only on in-sample accuracy.

## 14. Champion–challenger testing

The current production model is the champion.

New models must run as challengers before they can affect published picks.

A challenger should:

* Generate private predictions
* Save full prediction snapshots
* Be graded against actual outcomes
* Be compared with the champion
* Remain hidden from public users
* Require a minimum sample size
* Pass predefined performance requirements
* Require Master Account Holder approval before deployment

Do not automatically promote a challenger based on a short winning streak.

## 20. Development process

Implement this system incrementally.

For every step:

1. Inspect the existing backend and database first.
2. Preserve all working model behavior.
3. Explain the proposed database and code changes.
4. Create migration files.
5. Provide complete code for every changed file.
6. Add tests.
7. Run the tests.
8. Run the production build.
9. Fix every error.
10. Provide exact Git add, commit and push commands.

Begin with:

1. Database schema audit
2. Immutable prediction snapshots
3. Odds-history storage
4. Results grading
5. Closing-line capture
6. Performance analytics
7. Model registry
8. Dataset builder
9. Backtesting
10. Champion–challenger testing

Do not begin by replacing the existing TBM prediction logic.
