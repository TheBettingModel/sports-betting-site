TASK #224B-1 — MLB HISTORICAL COMPLETION-TIME & CHRONOLOGY PROOF

MISSION

Convert the current MLB historical foundation from date-ordered reconstruction into a genuinely point-in-time-safe chronological dataset by proving when each historical game result became final and preventing that result from influencing any later-game feature state until the prior game was actually complete.

This task exists because #224B produced:

- 9,393 canonical MLB games
- 18,786 team-game feature rows
- 9,393 separate outcome rows
- 9,076 offense-only partial candidates
- 0 core-eligible games
- 0 enhanced-eligible games
- 153 quarantined games
- 2,013 locked 2026 OOS candidates

Current blocker:

All 18,786 feature rows have unverified completion boundaries.

The historical schedule provides official dates but not yet authoritative completion timestamps.

Therefore:

- official-date ordering is only a proxy;
- same-day chronology is not proven;
- a game's outcome cannot yet safely influence another game's features;
- the dataset is NOT training-safe;
- MLB V4 training must NOT begin.

The sole objective of #224B-1 is to resolve this chronology gate as rigorously as possible.

DO NOT train MLB V4.
DO NOT retune V4/V4.1.
DO NOT modify production MLB V1.
DO NOT deploy.
DO NOT push.
DO NOT change NCAAF.
DO NOT start NFL V4.
DO NOT modify Apple/EAS credentials.
DO NOT manipulate Git history.

==================================================
CORE PIT RULE
==================================================

For any target game G:

A prior game P may influence G's pregame features ONLY if there is trustworthy evidence that P was complete before G's feature cutoff.

Required logic:

completion_time(P) < feature_cutoff(G)

If that cannot be proven:

P MUST NOT influence G.

No same-date assumption is allowed.

No schedule-order assumption is allowed unless backed by authoritative timing evidence.

No result may enter rolling offense, bullpen workload, pitcher history, or any other state before the game was actually complete.

SECTION 5 — SAME-DAY CHRONOLOGY
==================================================

This is the core problem.

For all games involving the same team on the same calendar day, explicitly establish chronology.

Examples:

Game 1
Game 2

Game 1 may inform Game 2 only if:

completion_time(Game 1) < feature_cutoff(Game 2)

If Game 2's pregame cutoff occurred before Game 1 ended:

Game 1 must NOT influence Game 2.

Do not assume doubleheader Game 1 always finished before Game 2 pregame state was known.

Handle:

- traditional doubleheaders
- split doubleheaders
- day/night doubleheaders
- delayed starts
- long extra-inning games
- resumed suspended games
- rain delays

==================================================
SECTION 6 — SUSPENDED / RESUMED GAMES
==================================================

Treat suspended games conservatively.

A suspended game's result is not complete until the game is officially completed.

If a game starts on Date A and finishes on Date B:

its outcome must not influence another game's features before final completion on Date B.

Track:

original_start_time
suspension_time if available
resume_time if available
final_completion_time

If safe chronology cannot be proven, quarantine the affected relationship/game.

==================================================
SECTION 7 — POSTPONED / RESCHEDULED GAMES
==================================================

Ensure postponed games use actual played chronology, not original scheduled date.

A game scheduled Monday but played Wednesday must enter historical state only after Wednesday completion.

Do not let original scheduled date influence chronological ordering.

==================================================
SECTION 8 — EXTRA-INNING GAMES
==================================================

Extra-inning games may finish materially later than standard-duration assumptions.

Therefore:

No estimated standard game duration may be used to determine completion.

Require real or high-confidence completion evidence.

SECTION 13 — DATE-ONLY FALLBACK POLICY
==================================================

Some historical games may never receive trustworthy completion timestamps.

Do NOT force them into training.

Classify them:

DATE_ONLY_UNSAFE

or equivalent.

Possible conservative handling:

- allow them only when no same-team target exists until a later calendar day with a sufficient safety margin
- OR quarantine entirely

If proposing a conservative date-boundary fallback, prove why it cannot leak.

Example:

If prior game occurred on Aug 1 and target game starts Aug 3, game completion by Aug 3 may be logically certain if official final status is known.

But formalize the rule.

Do NOT use same-day date-only chronology.

Any fallback must be documented separately from authoritative timestamps.

SECTION 20 — LEAKAGE TESTS
==================================================

Add specific chronology leakage tests.

At minimum:

1. Prior game completion must be before target cutoff.

2. Same-day result cannot enter target features unless actual completion is proven before cutoff.

3. Suspended game cannot enter state before final completion.

4. Postponed game uses actual played chronology.

5. Extra-inning duration cannot be estimated arbitrarily.

6. Target outcome cannot enter target features.

7. Later game cannot enter earlier features.

8. Doubleheader ordering is timestamp-based.

9. Date-only same-day ordering is rejected.

10. Completion timestamps cannot be created from DB insertion time.

11. Retrieval timestamps cannot masquerade as historical completion times.

12. Final-status timestamp provenance must be auditable.

13. Conservative next-day fallback, if used, must pass dedicated proof tests.

Any failure is a HARD FAILURE.
